# 四角色動作、合作補批與畫面分包第二輪稽核

日期：2026-09-20  
性質：唯讀程式碼稽核；本文件是本輪唯一寫入項目  
範圍：第一輪三項缺陷修正、封封 16 個動作與收劍中斷、菲菲近戰、合作雙席與缺號補批、追時、同種忍具先進先出，以及 `App.show()`／`App.startFight()` 的按需載入與失敗處理。封封動畫尚未接入以前的歷史狀態不再當作缺陷。

## 結論

第一輪找到的兩項中度與一項低度缺陷均已修正並有回歸測試。第二輪另外重現四項中度與一項低度缺陷：排隊後仍使用入列時的等待長度、兩張同動作的確認可能誤接到較新的本體、送出遭拒後殘留本機預演、`?motion=1` 預載拒絕使啟動停在標題前，以及上樓逐格素材拒絕造成未處理的非同步錯誤。五項均已修正，本輪複審通過。

修正後未再找到會改變引擎傷害、把命中套到另一隻同名魔物、讓舊載入覆蓋新畫面、卡住連續出牌，或在離場後留下動作畫布與計時器的可重現缺陷。這是程式呼叫路徑與自動測試結論；依任務要求未開瀏覽器，因此不把肉眼動作品質列為已驗證。

## 第一輪三項缺陷的關閉證據

### 1. 多段補批不再以單波時長提早推進

- 位置：`src/ui/screens/combat.ts:3412-3473`、`src/ui/qiuqiu-combat-motion.ts:72-108`。
- 現況：每張補批動作先從該張的命中切片、指定目標 UID 與閃避補波求出 `presentationWaves`，再以真實波數計算動作時長與展示等待。菲菲三波飛針為 980 毫秒，噹噹三波連拳為 1,020 毫秒。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:192-206` 驗證三波時長與等待；同檔命中測試驗證只取指定 UID 的命中。

### 2. 延遲確認可續播延伸波次，且不覆蓋下一張動作

- 位置：`src/ui/screens/combat.ts:413-425`、`src/ui/screens/combat.ts:598-615`、`src/ui/screens/combat.ts:2747-2777`、`src/ui/qiuqiu-combat-motion.ts:110-130`。
- 現況：每次本機預演取得單調增加的代次。確認落在延伸時長內時，只在代次仍與目前演員一致且本體已停止時恢復；若下一張同動作已開始，舊確認不會呼叫恢復或擴波。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:208-219` 驗證時間邊界、播放中不重啟與代次錯配拒絕。

### 3. 本機恢復忍具在補批中只消耗一次預演

- 位置：`src/ui/screens/combat.ts:421-425`、`src/ui/screens/combat.ts:2086-2104`、`src/ui/screens/combat.ts:3417-3423`、`src/ui/qiuqiu-combat-motion.ts:29-70`。
- 現況：卡牌以 UID、忍具以「座位＋忍具識別字」分列，列內先進先出；自己的忍具確認會取得既有 `eat` 預演，不再重播。雙席使用各自的座位鍵，不會互相消耗。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:221-245` 驗證同種忍具先進先出、清除與遭拒後同鍵重試。

## 第二輪新發現並已修正

### 中度 A：補批排隊時間沒有扣除等候期間

- 原觸發：菲菲三波飛針總長 980 毫秒，在另一項 700 毫秒展示後才開始。舊程式在入列時算出約 1,010 毫秒等待；輪到它時雖以 `elapsed` 追到第 700 毫秒，佇列仍再等完整舊值，使後續動作與結算多停約 700 毫秒。
- 修正：`RemotePresentationItem.wait` 可保存延遲函式；`pumpRemotePresentation()` 在 `item.play()` 後才呼叫 `resolveCombatMotionPresentationWait()`。本機項以原始 `localMotion.at` 在實際開始時重算，前例只再等 310 毫秒。
- 位置：`src/ui/screens/combat.ts:2398-2421`、`src/ui/screens/combat.ts:3468-3477`、`src/ui/qiuqiu-combat-motion.ts:93-108`。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:201-206` 先改變「現在時間」，再解析等待函式，結果為 310 毫秒。

### 中度 B：相同動作名稱不足以辨識是哪一張牌

- 原觸發：A、B 兩張牌都映射為菲菲 `shuriken`；B 已覆蓋演員後，A 的延遲確認仍只看席位與動作名稱，可能把 B 重設成 A 的追時或波數。
- 修正：本機紀錄、`CombatMotion`、`ActOptions` 與命中整合一路傳遞同一代次。A 的代次與 `state(B).presentationToken` 不同時，恢復與擴波兩條分支都跳過；B 輪到時才匹配。
- 位置：`src/ui/screens/combat.ts:413-425`、`src/ui/screens/combat.ts:598-615`、`src/ui/screens/combat.ts:2621-2630`、`src/ui/screens/combat.ts:2747-2777`。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:208-219` 明確驗證代次 7 不得匹配目前代次 8。

### 中度 C：送出遭拒會留下可被重試誤取的本機預演

- 原觸發：客戶端先記錄卡牌或忍具預演，若同步 `submit` 回傳失敗，或稍後由會話通知 `onDropped`，舊紀錄仍留在列內；重試同一 UID 或同種忍具時，確認會先取得舊時間戳與舊代次。
- 修正：`LocalMotionPresentationQueue` 追蹤精確的本次送出物件；同步失敗與 `onDropped` 都呼叫 `dropInFlight()`，同鍵重試只留下新代次。
- 位置：`src/ui/qiuqiu-combat-motion.ts:29-70`、`src/ui/screens/combat.ts:2090-2104`、`src/ui/screens/combat.ts:2154-2177`、`src/ui/screens/combat.ts:3313-3320`。
- 回歸證據：`tests/ui/qiuqiu_combat_motion.test.ts:234-245` 先移除代次 1，再確認同鍵只取得代次 2。

### 中度 D：`?motion=1` 預載拒絕會讓啟動停在標題前

- 原觸發：使用 `?motion=1` 進入一般遊戲，角色動作模組載入或任一動作圖片解碼拒絕。該區原本直接 `await`，拒絕會讓 `boot()` 在 `app.show('title')` 前中止，使用者只看到尚未渲染的空白舞台。
- 修正：只在該預載區加入局部拒絕處理；失敗時記錄一行錯誤、保留普通立繪並繼續顯示標題，不增加長警告或阻斷畫面。
- 位置：`src/main.ts:75-89`。
- 回歸證據：`tests/ui/main_motion_boot.test.ts:4-10` 驗證兩種角色預載均位於拒絕處理內，且 `app.show('title')` 位於退路之後。測試先在舊程式失敗，再於修正後通過。

### 低度 E：上樓逐格素材拒絕會留下未處理的非同步錯誤

- 原觸發：網址開啟動作模式，上樓轉場載入同伴動作模組或解碼圖片失敗；靜態轉場本身仍能走完，但 `loadWalkActor()` 的拒絕沒有處理，會產生未處理錯誤。
- 修正：動態載入鏈加入拒絕處理，保留原靜態角色、三秒換場與遮罩收尾。
- 位置：`src/ui/acttransition.ts:31-42`、`src/ui/acttransition.ts:68-82`。
- 回歸證據：`tests/ui/act_motion.test.ts:105-119` 讓預載明確拒絕，驗證換場只發生一次、遮罩移除且沒有建立須釋放的逐格演員。

## 指定範圍核對

### 封封動作與收劍

- `src/ui/fengfeng-motion-data.json` 實際有 16 個動作、128 格、11 張不重複來源圖；不是沿用文件中的推測數量。
- `src/ui/companion-motion.ts:126-141` 對應 32 張封封專屬牌；`tests/ui/companion_motion.test.ts:192-203` 逐張與正式牌庫及動作計畫交叉核對。
- 五種劍擊結束後由 `resolveFengfeng()` 接到短收劍，總時長含收劍但命中只讀攻擊中繼資料。新的 `actor.play()` 可立即取代收劍；測試以 `slash` 進入收劍後立刻播放 `guard`，第一格即換成架擋。
- 位置：`src/ui/companion-motion.ts:199-208`、`src/ui/companion-motion.ts:267-313`；測試在 `tests/ui/companion_motion.test.ts:213-227`。

### 菲菲近戰與原地施放

- `companionIsMelee('feifei', ...)` 只把 `attack1`、`kick` 視為近戰；飛針、針雨、分身、結印、防禦與恢復留在原位。
- `prepareMelee()` 還會再要求牌的真實種類為攻擊，技能牌即使映射到攻擊姿勢也不移動。
- 位置：`src/ui/companion-motion.ts:123-125`、`src/ui/companion-motion.ts:320-324`、`src/ui/screens/combat.ts:580-596`；測試在 `tests/ui/companion_motion.test.ts:204-211`。

### 合作雙席、補批、追時與 UID

- 角色演員以座位為鍵，玩家節點以 `data-seat` 取得；本機預演的忍具鍵也包含座位。
- 每張補批先以動作前後快照建立自己的命中與紀錄邊界，再按敵人 UID 建立命中計畫。兩隻同名魔物不會共用傷害、格擋、受傷或倒下展示。
- 本機追時使用原始送出時間；遠端補批按佇列真正開始的時間播放。換畫面時會清空補批列、命中計時器、投射物取消函式與所有演員。
- 位置：`src/ui/screens/combat.ts:413-425`、`src/ui/screens/combat.ts:2398-2432`、`src/ui/screens/combat.ts:3397-3510`。

### 按需畫面、戰鬥暖機與舊請求

- `src/ui/lazy-screen.ts:16-32` 同時以請求序號與目前畫面名稱守衛；先前請求完成或拒絕時，不能覆蓋已離開的畫面，也不能覆蓋同畫面的較新參數。
- `src/ui/app.ts:374-425` 讓戰鬥模組與本場素材暖機並行；素材或模組其中一項拒絕仍會結束暖機。若戰鬥模組仍不可用，延遲畫面負責顯示明確錯誤，不讓拒絕逸出。
- `src/main.ts:52-73` 先同時載入動作試玩與戰鬥登記，再啟動試玩；失敗時顯示可重新整理或回標題的畫面。
- `src/main.ts:75-89` 的一般 `?motion=1` 入口也有獨立退路；逐格預載失敗時繼續普通標題，不與動作試玩的錯誤畫面混用。
- 回歸證據：`tests/ui/lazy_screen.test.ts` 驗證離開後舊請求、同畫面重入與拒絕三條路徑；`tests/ui/act_motion.test.ts` 驗證轉場取消、晚到演員釋放與載入拒絕；`tests/ui/main_motion_boot.test.ts` 驗證一般動作模式的啟動退路。

## 封封引擎另冊稽核

動作稽核完成後，獨立引擎稽核另行重現三項非動作缺陷與一項低度提示差異：合作戰後倒下席無法載回、同名能力重打會先付費再由效果層靜默略過、零蜷縮的噹噹攻擊會把封封下一擊支援強造成傷害事件，以及唯一存活同伴已結束回合時沒有提示等待下一回合。四項均已用先紅後綠測試做最小修正，並由原稽核代理以原重現、升降版邊界、跨角色傷害與支援對象案例獨立複審通過。完整觸發證據、修法與複審結果另見 `docs/fengfeng-engine-code-audit.md`，不混入本文件的動作缺陷計數。
