### 高 1 — 鐵砂衣會在開戰那一瞬間把球球打死，而且畫面上沒有任何交代

`src/content/relics.ts:87-88`（`combatStart: [{ kind: 'selfDamage', amount: 4 }]`）
→ `src/engine/combat.ts:55-58`（`startCombat` 在 `startPlayerTurn` 之前跑 `combatStart` 鉤子）
→ `src/engine/actions.ts` `damagePlayer`（`opts.direct` 那一支不看蜷縮，血歸零就 `cs.phase = 'lost'`）

實測（探針 probe2）：帶著鐵砂衣、`hp = 4` 進 `wood_dummy`，回來的戰鬥狀態是 `hp = 0`、`phase = 'lost'`、手牌 0 張，戰鬥紀錄裡只有魔物的開場白，**連一行「鐵砂衣扣了 4 點」都沒有**。玩家看到的是：走進戰鬥、畫面閃一下、直接陣亡，完全不知道發生什麼事。這條路只要在貓窩沒睡飽、血低於 5 就會踩到。

修法：`selfDamage` 走秘寶來源時加地板（`amount = Math.min(amount, cs.player.hp - 1)`），或在 `damagePlayer` 對 `source === 'relic'` 的開場自傷保底留 1 血；不管選哪個，都要補一行 `log(cs, '鐵砂衣的重量壓下來，扣了 4 點生命')`。

### 高 2 — 關主先倒、僕從後倒時（波斯大小姐那場），已經消散的關主會「復活」再演一次倒下

`src/ui/screens/combat.ts:519`
```ts
if (e.dead && !reviving) cls.push(bossUnit && cs.phase === 'won' ? 'boss-fall' : 'gone');
```

`persian_lady` 是唯一多單位的關主戰（`src/content/enemies.ts:1097`，`['butler_cat', 'persian_lady', 'maid_cat']`，我用 60 個種子跑過確認陣容）。時序是：

1. 關主先被打倒時 `cs.phase` 還是 `'player'` → 節點拿到 `gone`，加上 `combat.ts:1183` 補的 `dead` → 溶解動畫、`.combat .unit.gone:not(.dead)`（`combat.css:153`）之後把它藏起來。畫面上關主已經不見了。
2. 玩家再出一張牌打死最後一隻僕從 → `cs.phase` 變 `'won'`。**玩家出牌走的是整頁 `render()` 不是 `patchField`**（`combat.ts:1138` 的 `opts.light` 只有 `1069`、`1085` 兩處敵方回合會傳），關主節點被重建。
3. 重建後的類別是 `boss-fall`，**沒有 `gone`、也沒有 `dead`**（`dead` 只在死亡那一拍由 JS 加）。`.boss-fall` 沒有任何隱藏規則，於是那具已經消散的屍體重新出現，照 `combat.css:889-895` 的 `boss-fall` 關鍵影格從 `brightness(2.6)` 全白開始，往前倒 1.7 秒。

玩家看到的就是「已經死掉不見的波斯大小姐突然亮起來又倒一次」。

修法：不要用「當下的 `cs.phase`」決定，改成在關主倒下的那一拍就定案。例如在畫面層記一個 `fellUids: Set<number>`，`enemyUnit` 判斷 `bossUnit && fellUids.has(e.uid) ? 'boss-fall' : 'gone'`，並在死亡那一拍才把 uid 放進去（同時保持只放一次，重建也不會重播）。

### 高 3 — 伏兵的畫面吐槽是死碼，永遠不會出現

`src/ui/screens/combat.ts:1209`
```ts
if (cat && acting.size > 0) {
  ...
  if (fresh.some((l) => l.startsWith('伏兵'))) toast('有伏兵跳出來了喵！', '球球');
}
```

伏兵是在 `beginEnemyTurn` 裡冒出來的（`src/engine/combat.ts:239-250`），而 `runEnemyTurn`（`combat.ts:1066-1069`）的順序是：

```ts
const before = snap(cs);
if (!beginEnemyTurn(cs)) { settle(before, { deal: true }); return; }
settle(before, { light: true });      // ← 伏兵那句紀錄就在這一拍
```

這一拍**還沒有任何魔物出手**，`acting` 是照「`turnCount` 有沒有往前走」建的（`combat.ts:1147-1154`），所以 `acting.size === 0`，整個 `if` 區塊被跳過。下一拍 `fresh` 已經不含那行了（`b = snap(cs)` 重新取過）。我在探針裡確認過援軍剛出場時 `turnCount === 0`，`beginEnemyTurn` 也不會動任何人的 `turnCount`。

也就是說「畫面吐槽」這條驗收要求實際上沒達成，玩家只看得到一團煙（`combat.ts:1211` 的召喚煙）跟左上角紀錄。

修法：把伏兵那一行搬出去，跟召喚煙那個迴圈放在一起，只看 `fresh` 不看 `acting`。

### 中 5 — 結局師父的第一句踩掉專案自己訂的「師父只講大俠貼圖標題」規矩，而守門測試看不到

`tests/content/dialogue.test.ts:30-34` 有一條規矩測試「師父（tower_master）只講大俠貼圖標題」，白名單是 `['難逢敵手','走火入魔','退隱江湖','閉關','承讓','重出江湖','深藏不露','在下不才','來也']`。測試檢查的是**靜態的** `dialogue.victory`（那句還是 '承讓。'，所以通過），但實際播出去的是 `victoryLinesFor()` 換過的句子（`src/ui/app.ts:290`），三句全部不在白名單裡。

這可能是使用者刻意放寬（想讓結局更有溫度），但目前狀態是「規矩還在檔案裡、測試還在綠燈、行為已經違反」。修法二選一：把新句改寫成貼圖標題語感（例如把 '承讓。' 換成 '深藏不露。' / '難逢敵手。'），或明確廢掉這條規矩、同步改測試改成檢查 `victoryLinesFor()` 的輸出。

### 中 6 — `victoryLinesFor` 的門檻讓「承讓。」幾乎變成死內容，而且蜷縮流幾乎必中

`src/content/dialogue.ts:387-401`

實測（探針 probe1／probe2）：

- 只算 10 張起始牌，分類就已經是 `{ strength: 0, stealth: 1, block: 4 }`，門檻是 `top[1] >= 4` → **開局第一秒就判定蜷縮流**，`victoryLinesFor(STARTER_DECK, 1)[1].text` 回的是「護得住自己，就護得住別人。你出師了。」
- 全牌庫 96 張裡，`"block"`／蜷縮命中 14 張、隱身／潛水 10 張、爪力只有 **7** 張。想蓋過起始牌組的蜷縮基底，爪力流得堆到 5 張以上（全遊戲只有 7 張可拿）。
- 那 7 張裡 `fengkou`／「忍術·封口術」（`src/content/cards.ts:78-80`）是 `removeStatuses: ['爪力','貓步']`＝**拆掉敵人爪力**的牌，卻被算成球球的爪力流。

結果就是「都不明顯就照舊『承讓。』」這條退路實務上碰不到，而牌組傾向也分不太準。

修法：改成相對判準（例如某一類要佔牌組 25% 以上、而且要領先第二名 2 張以上才算），並把 `removeStatuses` 這類「對敵人做的」效果排除在外（比對 `target === 'self'` 而不是整串 `JSON.stringify`）。

### 中 7 — `show('combat')` 被延後之後，畫面上的按鈕還按得到（連點會多跑一次 `beginCombat`）

`src/ui/app.ts:216-244`

`go()` 的順序是：**先同步** `this.cs = beginCombat(run, encounterId)`（這步已經吃掉 `run.restBlock`＝暖毯的蜷縮、也推進了 `run.rng`），**再** `void warmEncounter(...).then(proceed, proceed)`，`this.show('combat')` 在 `proceed` 裡。冷圖的情況這中間最多空 1.5 秒，畫面還停在地圖／事件結果頁：

- 事件結果的「開打」鈕（`src/ui/screens/event.ts:223`）**沒有停用也沒有防重入**，連點兩下就是兩次 `beginCombat`：第一場的暖毯蜷縮白白被清掉（`run.restBlock = 0` 已經寫回去了）、亂數多推一次，第一個 `proceed` 被 `this.cs !== cs` 擋掉所以畫面只開一次（這點是對的）。
- 地圖上再點另一格會走到 `chooseNode`（`src/engine/run.ts`，`if (!n) throw new Error('不能走到 ...')`），變成點擊處理常式裡的未捕捉例外——不會壞存檔（`chooseNode` 已經把 `currentNode` 推到第一格，同層的其他格不在 `nextChoices` 裡），但主控台會噴錯、玩家只覺得「按了沒反應」。

改動前 `show('combat')` 是同步的，按鈕當場就被換掉，所以這是這批改動新引入的競態。

修法：`startFight` 進來就設一個 `this.pendingFight = true` 的重入鎖（`proceed` 或例外時解開），或在 `go()` 一開頭先鋪一層擋點擊的透明層／先 `show('combat')` 再暖機。

### 中 8 — 塔頂那組伏兵不是「小怪」，而且註解與行為不符

`src/content/enemies.ts:1085`（`miasma_blob` 第 4 回合叫 `paper_crane`）

順帶一提：「援軍帶難度魔氣」這條驗收要求**是達成的，而且超額**（連遭遇本身的 `hpScale`／`strength` 都繼承了）。問題只在難度預期與註解對不上，而 `tests/engine/ambush.test.ts` 只測了河童那組、沒有驗到這一組的數值。
