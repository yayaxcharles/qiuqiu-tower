### 中-1　名詞表附註誤解讀「保留」，守護符的說明會被錯誤地多寫一行

`src/ui/tooltip.ts:18`（`APPENDIX_SKIP` 清單）對上 `src/content/relics.ts:71`

守護符的說明是「回合結束時**最多保留** 8 點蜷縮到下一回合。」——這裡的「保留」是白話動詞（留著），但名詞表裡剛好也有一個叫「保留」的**牌面關鍵字**（`src/content/glossary.ts:50`：「回合結束時這張牌留在手上，不會被棄掉。」）。`glossaryLines()`（`tooltip.ts:19-28`）不管詞性、只做字串比對，「保留」沒有被排進 `APPENDIX_SKIP`，於是玩家把滑鼠移到守護符上，會在說明底下多看到一行「保留：回合結束時這張牌留在手上，不會被棄掉。」——講的是完全不相關的牌面規則，會誤導玩家以為守護符跟手牌有關。這條路徑在狀態列（`src/ui/hud.ts:73`）跟結算畫面（`src/ui/screens/result.ts:35`）都會重現，不是單一畫面的偶發狀況。

其他同類型的詞（消耗、看破、破功、定身、反彈……）逐一查過秘寶跟忍具全部 78 筆文字，只有這一處撞名；`iron_sand_vest`（`relics.ts:87`）講同一件事卻用「留」不用「保留」，剛好閃過這個坑，側面說明這是措辭巧合，不是刻意設計。

修法：把 `保留` 加進 `APPENDIX_SKIP`（跟已經在清單裡的「防禦」「蜷縮」同一類——太容易在白話句子裡被借用的常見字，不適合自動展開）；或者把 `guard_charm`／`iron_sand_vest` 的文案統一改成「留」，繞開這個字。

### 中-2　忍具鎖格只修了看不到的狀態列，戰鬥中真正在用的那排忍具沒有跟著改

`src/ui/screens/combat.ts:616`

這批的目標是「格數不要一局兩格一局三格」，但 `src/ui/hud.ts` 的忍具格**在戰鬥中是被 CSS 藏起來的**（`hud.ts:16-19` 自己的註解就寫「戰鬥中這一列的生命與忍具兩格是用 CSS 隱藏的」）。玩家在戰鬥裡真正看得到、也會點下去用忍具的，是 `src/ui/screens/combat.ts` 另外一份獨立實作的忍具列（`combat.ts:615-630`），這份完全沒有改：迴圈仍然是 `for (let i = 0; i < potionCapacity(run); i++)`，宗師難度以上一樣只畫 2 格、忍具袋／九命鈴一樣照實加格，沒有「至少畫 3 格＋鎖格」的處理。

也就是說，玩家最常遇到「這局忍具格怎麼變少了」的場合（戰鬥中，決定要不要按下忍具的當下），這批修改完全沒有觸及；真正被修到的狀態列忍具格，玩家反而只有在戰鬥外（地圖、事件、商店……）才看得到。這不會導致按錯或用不到忍具（`combat.ts:627` 的點擊只掛在真的有忍具的格子上，邏輯本身沒壞），純粹是這批想解決的「格數忽多忽少」體驗問題，在最關鍵的畫面上還在。

修法：把 `hud.ts:80-92` 那段「`Math.max(cap, 3)` ＋鎖格」的邏輯搬一份到 `combat.ts:616` 的迴圈，資料來源換成 `cs.potions[i]`（戰鬥中的即時值，而不是 `run.potions`），鎖格沿用 `.hud-potion.locked` 的做法或另開一個 `.potion.locked` 樣式。

### 中-3　狀態列代碼改成按鈕之後，「空間不夠就縮」的安全機制被自己蓋掉了

`src/ui/styles/components.css:162` 對上 `:557-559`

狀態列本來就有一條專門處理「東西放不下」的規則（`components.css:557-559`）：

```
/* 頂列的鈕與數字一律不折行、不被壓扁——空間不夠時由「本局代碼」那格負責縮 */
.hud .btn, .hud-floor, .hud-fish, .hud-relics, .hud-potions { white-space: nowrap; flex: none; }
.hud .hud-seed { min-width: 0; flex: 0 1 auto; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

設計是「所有按鈕與數字都不准縮，只有代碼那一格可以被擠小、擠不下就用刪節號」。問題是新的代碼按鈕**同時符合兩條規則**：它有 `.btn`，也有 `.hud-seed`。這兩條選擇器的優先度（specificity）相同，寫在後面的 `:559` 蓋過 `:558`，所以 `flex: 0 1 auto`（可以縮）確實贏了、沒有變成完全不能縮，這部分沒問題；但這批另外加的 `:162`：

```
.hud .hud-seed.btn { opacity: 1; font-size: inherit; text-shadow: none; overflow: visible; }
```

選擇器多一個 class、優先度更高，把 `overflow` 從 `hidden` 蓋成 `visible`。而 `text-overflow: ellipsis` 依 CSS 規格**只有在 `overflow` 不是 `visible` 時才有作用**——換句話說，`:559` 準備好的「擠不下就顯示…」這條退路，被 `:162` 悄悄關掉了。等於現在的代碼按鈕「可以被擠縮」但「擠縮時不會乾淨地截斷」，超出的內容會直接蓋到旁邊的音樂／音量／音效控制項上，而不是像設計原意那樣安分地縮小。

這不是憑空的邊界狀況：秘寶格 `.hud-relics`（`components.css:82`）沒有數量上限，`for (const id of run.relics)` 整局收到幾件就畫幾件（`hud.ts:64`），一輪破關前段累積十件以上秘寶並不罕見。粗抓一輪典型狀態列寬度（樓層 ~60、血條 220、小魚乾 ~75、8 件秘寶 ~322、忍具 3 格 108、牌組鈕 ~105、圖鑑鈕 ~80、代碼鈕(新) ~80、音樂/音量/音效 ~228、11 個間距 110）粗估已經逼近甚至超過狀態列可用寬度（1280 − 左右內距 28 ＝ 1252px）——這只是粗算示意（文字寬度沒有拿實際字型量過，跟上一份稽核算牌面字體用的精確度不能比），但方向很清楚：代碼按鈕一旦真的被擠縮，現在的退路是「文字溢出蓋到別的按鈕」而不是「乾淨顯示省略號」。

值得一提：舊版代碼是純文字「本局代碼 1788671234567 ⧉」（13 位數字），比新的「📋 代碼」明顯長，所以這批改動本身**降低了**觸發擠壓的機率；只是一旦真的被擠到，失敗的樣子比以前難看。

修法：`:162` 那條加一行 `flex-shrink: 0`（或整條改成 `flex: 0 0 auto`），讓代碼按鈕跟其他按鈕一樣「不縮」，不要再指望它當安全閥——反正這批的初衷就是让代碼佔的空間變小，不縮也應該放得下；真的放不下時，情願讓別的東西（例如秘寶格）換成可以橫向捲動或超過一定數量就摺疊，而不是靠代碼按鈕犧牲。

### 低-3　老闆立繪翻面後，進場滑入的方向可能跟著鏡射反過來（影響很小、幾乎看不出來）

`src/ui/styles/screens.css:705` 對上 `src/ui/styles/base.css:188-190`

`portrait-in` 的 keyframe 只動 `transform`（`translateX(-22px) scale(.96)`）跟 `opacity`（`base.css:188-190`），確認沒有動獨立的 `scale` 屬性，所以商店這條 `scale: -1 1`（`screens.css:705`）不會被進場動畫蓋掉——這點原本的顧慮是多餘的，翻面本身沒問題。

但兩個獨立屬性疊加時的套用順序是「先套 `transform`，再套 `scale`」，商店的立繪進場那 260 毫秒，`translateX(-22px)` 是在鏡射**之前**套用的位移，鏡射會把這個位移的方向也一起翻過來——**可能**造成商店老闆滑入畫面的方向跟其他畫面（貓窩、事件都是從左滑入）相反，變成從右邊滑入。這純粹是 260 毫秒進場動畫的方向細節，跟老闆立繪定住不動之後的最終位置、陰影完全無關（陰影是 `0 8px 16px`，水平位移 0，鏡射不影響），也沒有測試或畫面驗收能百分之百確認觀感——標成「可能」是因為多層 `transform`/`scale`/`transform-origin` 疊加的實際渲染順序沒有實機截圖比對，只靠規格書推導。

修法：不影響功能，可以不用管；真的在意方向一致，可以把商店的進場動畫改成 `translateX(22px)`（正負號對調）單獨處理，或乾脆讓商店老闆跳過滑入動畫、直接淡入。

## 查過確認沒問題的

**提示框補名詞說明（`src/ui/tooltip.ts`）**

- 長詞排前面確實有效：`TERMS` 依字數由長到短排序再組進 `RE`（`tooltip.ts:6`），JS 正規表達式的 `|` 在同一個起始位置會照順序試、選第一個成功的，所以「下回合隱身」「下回合蜷縮」「不可打出」這種長詞會贏過裡面包含的短詞，不會被拆成一截一截——這套技巧本身沒問題。
- `不可打出` 這個詞會被自己的定義重複解釋（`combat.ts:102` 的 `reason: '不可打出'` 本身就是這個詞，滑上去等於先看到裸詞、再看到解釋），但這是「補充說明」而不是「講錯」，效果是讓原本看不懂的裸詞多了解釋，屬於這批的正向作用，不算問題。
- 藥水（`src/content/potions.ts` 全 20 筆）文字裡沒有出現「消耗」「保留」等會撞名的詞，這個具體情境目前不會發生（撞名的是秘寶守護符，已列中-1）。
- 能力牌（`src/ui/screens/combat.ts:401` 那顆 `describeCard` 呼叫）目前不會印出「消耗。」「保留。」——`src/engine/types.ts:8` 定義的四個關鍵字裡，會被印成這兩句的牌全部檢查過，全庫沒有任何 `type: 能`（能力）牌帶 `消耗` 或 `保留` 關鍵字，這條路徑目前是死路，不會誤觸發（`cardtext.ts:191-192` 那兩行本身留著沒問題，只是暫時用不到）。
- 難度說明（`hud.ts:151`／`content/difficulty.ts:11-17`）掃過五級文字，「忍具」「罐頭鋪」「大魔物」都在 `APPENDIX_SKIP` 名單裡，不會誤加說明。
- 圖鑑疊層 `z-index:70` 對提示框新的 `z-index:100`（`base.css` 該行）：查過圖鑑的疊層宣告，100 確實比 70 高，提示框滑上去看得到，這個改動有達到目的。

**事件升級加確認（`src/ui/screens/event.ts`）**

- `showUpgradeConfirm` 開著時底下點不到東西：見「高」一節的說明，`inert` 鎖的是整個 `#screen`，HUD 按鈕跟舊選項都在裡面一起被鎖住。
- `openPicker()` 用 `cancellable: false` 是延續原本就有的設定（這行在這批之前就是 `false`，不是新加的），跟貓窩磨爪（`src/ui/screens/rest.ts:65-66`，用的是 `cancellable: true`）刻意不同：事件裡選了「升級一張牌」這個結果就不能整個反悔，但可以透過「再看看」無限次換牌重選，直到真的按下「就磨這張」——這是原本就有的規矩，這批只是把「選完直接升級」改成「選完先看預覽再問一次」，沒有動到能不能整個放棄升級這件事。
- `want > 1`（一次升兩張以上）跟移除牌兩條路都還是走 `onPickMany` / 直接 `settleCards`，不會經過新加的確認框——這點維持這批說明裡講的「原路」，沒有意外把確認框套到不該套的地方。
