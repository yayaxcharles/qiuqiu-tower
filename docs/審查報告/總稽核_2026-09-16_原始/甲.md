## 一、問題清單

### 高-1　換忍具視窗還開著時，同伴一有動作就再疊一個；兩個都按「換」，兩支舊忍具被同一支新的換掉（主機、客戶端都中）

- **位置**：`src/ui/screens/reward.ts:320-327`（排問話只看 `line.isConnected`，沒有「正在問」的記號）；觸發重畫的是 `reward.ts:156`、`:160`、`:164`、`:166` 四個 `app.show('reward', r, { quiet: true })`。
- **情境**：B 忍具滿了，進戰利品頁 350 毫秒跳出換忍具視窗。B 還在想換哪一支，A 挑了秘寶或挑了牌 → B 那台整頁重畫 → 新畫出來那一列又排一次 350 毫秒的問話 → **第二個一模一樣的視窗疊在上面**。A 動幾下就疊幾個（實測：同伴挑秘寶＋挑牌，疊到 3 個）。
  - B 按掉最上面那個「不換」，底下還有一個 → 這就是使用者回報的「按我不要之後又會跳出來，A 玩家選東西、B 玩家就會又跳一隻選忍具」。今天的 `potionDeclined` 只修到「答完之後才重畫」那一種；**視窗開著時重畫**這一種沒修到，而且這一種更常見（視窗 0.35 秒就跳、玩家想好幾秒，同伴通常就在這幾秒挑完牌）。
  - B 兩個視窗都按「換」（不同格）→ 兩台一致地變成兩支煙霧彈、少了兩支舊的。不會斷線，但東西不見。
  - 鎖畫面的計數沒有壞：全部視窗關掉後 `#screen` 的 `inert` 有拿掉。
- **修法**：比照升級挑牌那條的 `upsAsking`，在 `r` 上記「正在問」（開視窗前設、回呼裡清），排問話前、以及 350 毫秒計時器觸發的當下都檢查 `正在問／potionSwapped／potionDeclined`。
- **重現**：有。
  - `potion_swap.test.ts`：主機疊 2 個、兩個都換後 `smoke_bomb,smoke_bomb,firecracker`；客戶端疊 2 個、按「不換」後還剩 1 個；有兩件秘寶的大魔物戰利品疊到 3 個。
  - `two_machines.test.ts`（兩台真畫面）：A 點一張牌 → B 疊 2 個 → B 都按換 → A、B 兩台看到 B 的忍具都是 `smoke_bomb,smoke_bomb,firecracker`，指紋一致、沒有分岔。

### 中-1　客戶端按「換」之後、主機編號繞回來之前只要重畫一次，就會再問一次（主機不會中）

- **位置**：`reward.ts:310`（要不要問只看 `r.potionSwapped`）；`reward.ts:146`（這個記號要等 `onRunApplied` 收到自己那一則才設）；`src/ui/potionswap.ts:63`（連線時只送出、不回報）；`reward.ts:321` 計時器觸發時不再看記號。
- **情境**：客戶端換掉第 1 支 → 請求還在路上 → 同伴挑牌（或自己緊接著挑牌）→ 重畫時那一列又寫回「忍具帶滿了，收不下」→ 350 毫秒後再問。**就算編號在這 350 毫秒內繞回來也照問**，因為計時器不看記號、而只有換忍具的那一批不會觸發重畫。玩家以為剛剛沒換成功（狀態列也還是舊的，見低-1），再換一支 → 兩支都被換掉。
  - 平常一個來回一兩百毫秒，窗口窄。**斷線接回期間**（今天早上的功能）請求會排隊好幾秒到兩分鐘，而戰利品頁不擋操作（只有戰鬥與罐頭鋪看 `suspended`），自己挑一張牌就中。
  - 主機的動作是同步套用，`swapPotion` 回來之前記號就設好了，實測不會中。
- **修法**：換的當下就在 `r` 上把 `potionSwapped` 設起來（讓 `swapPotion` 回傳有沒有送出去）；計時器觸發時再查一次記號；`onRunApplied` 不再用「收到換忍具動作」來推「這一頁換過了」（順便解掉中-2）。
- **重現**：有。`potion_swap.test.ts` 第 1 條（同伴挑牌、編號晚到 → 再問 → 再換一次變 2 支煙霧彈，兩台指紋一致）、第 6 條（線路扣住時自己挑牌也會再問）。
  - 附帶：第一版測試沒先讓補跑（`setTimeout 0`）跑完就放編號回來，結果沒重現；真實時間裡補跑幾毫秒就跑完、一定比編號早，所以測試改成先推 5 毫秒再放編號。

### 中-2　上一格事件頁換的忍具，動作漏到下一場戰利品頁，被當成「這一頁換過了」→ 收不下的那支完全不問、清單還寫「獲得忍具」

- **位置**：`reward.ts:146`（凡是我這個座位的換忍具動作都算，不看是不是這一頁送的、換的是不是這一支）；`src/net/session.ts:704`（沒有畫面接的整局動作進 `unhandledRun`）；`session.ts:219`（回地圖時只丟掉「走進上一格之前」的，同伴已經投過下一格的票就會留下）；`session.ts:292`（下一個註冊 `onRunApplied` 的畫面補收）。事件頁、地圖、戰鬥三個畫面都不註冊 `onRunApplied`（全倉只有戰利品、紙箱、貓窩、罐頭鋪有）。
- **情境**：事件拿到忍具收不下 → 我還在想換哪支時，同伴已經按「繼續」回地圖投了下一格 → 我換了 → 這則動作沒人接、而且帶著較新的票數，回地圖過濾時被留下 → 下一格是戰鬥（戰鬥不接）→ 戰利品又掉一支我收不下的忍具 → 戰利品頁一註冊就補收那則舊的換忍具 → `r.potionSwapped = true` → 同伴先挑過牌的話，補跑造成的重畫比 350 毫秒早 → 那一列整個消失、不問，清單寫「獲得忍具「煙霧彈」」，實際沒進背包。
  - 客戶端在戰利品頁換完、馬上挑最後一張牌離開，編號晚到地圖，也走得到同一條。
- **修法**：同中-1——記號在本頁送出時就設，`onRunApplied` 裡換忍具那一段只負責「不重畫」、不再設記號；或換畫面時把 `unhandledRun` 裡的換忍具動作丟掉（它沒有畫面需要補收）。
- **重現**：有，但**事件頁畫面本身沒跑**：`swap_leak.test.ts` 直接呼叫 `submitRun`、`clearScreenHooks('map')`、`syncRun` 把「事件→地圖→戰鬥」的會話狀態重建出來，再畫真的戰利品頁。結果：不問、`potionSwapped` 為真、清單寫「獲得忍具「煙霧彈」」、背包裡沒有。
