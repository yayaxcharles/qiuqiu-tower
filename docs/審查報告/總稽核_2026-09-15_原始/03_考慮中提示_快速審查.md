## 1. `src/net/session.ts` 的 `handle()`

**結論：這一條沒問題。**

- 位置正確（`session.ts:478`）：`hint` 擺在 `pick`／`drop` 後面、`handleRun` 與所有 `cs` 檢查**之前**，跟註解說的「開局訊息在 attach 之前就會到」同一個理由。`attach` 之前收到 → `this.hinted` 還是 `null` → `?.()` 直接吞掉，不碰 `cs`、不碰佇列，不會炸。
- 戰鬥結束後到達：若已換畫面，`App.show()`（`src/ui/app.ts:126`）會叫 `clearScreenHooks`，而 `hinted` 已加進清單（`session.ts:180`），所以收不到；若戰鬥畫面還在（結算動畫中），回呼第一行 `if (app.cs !== cs) return;`（`combat.ts:2452`）擋住，最壞只是多重畫同伴那一格。
- 自己送的：`if (m.seat !== this.seat)` 擋掉自我回聲，就算中繼哪天改成廣播也不會自打自臉。
- **舊版客戶端**：連不上，所以根本收不到。兩條路都有版本閘——房號路在中繼比對打包編號，不同就用 4400 關掉加入的那一位（`worker/src/index.ts:72-73`、`CLOSE.version` 在 `:42`）；貼碼路在 `src/net/code.ts:88,92` 比 `Q1` 與 build。萬一真的漏過去，舊版 `handle()` 對 `m: 'hint'` 是：`handleRun` 回 false → 兩個 `sync` 不中 → `start` 不中 → `switch` 只有 `req`/`act` 兩個 case、沒有 `default` → 安靜離開，不會停局也不會報分岔。

## 2. `combat.ts` 的 `setTargeting`

- **沒有漏網的直接賦值**：grep 全檔 `targeting`，賦值只有兩處——`combat.ts:440` 宣告 `let targeting: Targeting = null;` 與 `combat.ts:448` `setTargeting` 內部那行；其餘 10 處全是讀取或改走 `setTargeting`。乾淨。
- **`hintSent` 每場重建**：`let hintSent`、`mateHint` 都宣告在 `registerScreen('combat', …)` 的回呼裡（`:446`、`:453`），而 `app.show()` 是「每次都整個清空重畫」（`src/ui/app.ts:61`），每一場戰鬥都重跑一次回呼 → 新閉包、新 Map。**不會殘留**。
- **單機保護夠**：`const session = props.session ?? app.coop`（`:330`），`setTargeting` 寫的是 `if (session && u !== hintSent)`，單機 `session` 是 null 就整段跳過；`session.hint()` 自己還有 `if (this.dead) return;`；兩個傳輸層送出前都檢查 `readyState`（`rtc.ts:58`、`ws.ts:97`），斷線時不會丟例外炸掉點牌。

**中-1｜回合號用「收信端」的 `cs.turn` 蓋章，錯過就不會補送。** `combat.ts:2455` 存的是我這台當下的 `cs.turn`，但畫的時候要 `hint.turn === cs.turn` 才算數（`:421`）。兩台的回合推進是各自跑完動畫才前進的（同伴分頁被瀏覽器降頻時差更大）：同伴那台已經進到第 N+1 回合、馬上點牌，我這台還在演第 N 回合的魔物 → 這則提示被蓋成 N，等我跳到 N+1 就再也畫不出來。而且因為 `hintSent` 仍等於那張 uid，同伴不重新點就**不會再送一次**，這一整個回合的「考慮中」就沒了。不會壞狀態，但正是這個功能最常見的失效情境。

**中-2｜送方 `hintSent` 與收方 `mateHint` 會分岔。** `onCard`（`:1541`）對不用選目標的技能牌是直接 `play(uid, undefined)`，**不動 `targeting`**；拖曳出牌那條也一樣。於是：同伴選了攻擊牌 A（送 uid）→ 又點一張技能牌打出去 → 我這邊 `onApplied` 無條件 `mateHint.delete(a.seat)`（`:2469`，只認座位不認 uid）→ 「考慮中 A」消失，但同伴那台 A 其實還選著、`hintSent` 還是 A，所以永遠不會補送。刪除改成「只有打出的 uid 等於 hinted uid 才刪」就能避開。

**中-3｜完全沒有節流，免費額度有被單人點爆的空間。** 見第 4 條。

**中-4｜`tests/ui/mateplay.test.ts` 的護欄比看起來弱。** `expect(SRC).not.toMatch(/\n\s*targeting = (?!t;)/)` 只擋「換行＋空白後直接 `targeting =`」。改動前最典型的寫法 `onclick: () => { targeting = null; render(); }`（原 `:1380`）是行內的，前面有 `{ `，這條正則**抓不到**。也就是說最可能被重新寫回去的那個形狀，測試不會紅。

**低-1｜`hint` 同名遮蔽。** `playerUnit` 裡新增的 `const hint = …`（`:420`）跟外層那個放紅字提示的 `let hint = ''`（`:473`）同名。功能上沒事（函式內完全遮蔽、先賦值再用），但這個檔案裡 `hint = ''` 出現四次，之後有人在 `playerUnit` 裡想清紅字會踩到。

**低-2｜拖曳出牌不送提示。** 用拖的那一派玩家，同伴永遠看不到「考慮中」。屬設計取捨，但兩種操作體驗不一致，值得記一筆。

## 3. `onHint` 回呼

- **對白／開場階段安全**：`root.querySelector('.unit.player[data-seat=…]')` 在場上還沒畫出來時回 `null`，而程式是 `if (q && node)` 才替換（`combat.ts:2456-2458`）。重點是 **Map 先更新、DOM 後找**，所以就算這次找不到節點，等整頁重畫時照樣畫得出來。`cs` 在進畫面前就存在，`q.hand` 讀得到（同伴的手牌本來就在鎖步狀態裡）。
- **`mateHint` 的 turn 判斷**：見中-1。方向反過來（我比同伴快一個回合）倒是安全的——多留的那張會被 `mateHint.delete` 或下一次 turn 比對清掉。
- **舉手（ready）不會殘留**：`onEndTurn`（`:1710-1712`）在 `canAct()` 之後第一件事就是 `setTargeting(null)`，該送的 null 有送出去，收方刪掉 `mateHint` 後只重畫那一格，接著 ready 的動作走鎖步進來再畫一次「已結束回合」。這條路是通的。（`canAct()` 為 false 時 `onEndTurn` 會早退不送 null，但那種狀態下按鈕本來就按不動，沒有實際破口。）

**低-3｜`hint(null)` 掉包會卡住「考慮中」，但會自己過期。** 中繼在對方正在關閉時是 `try { … } catch {}` 直接吞掉（`worker/src/index.ts:108`），hint 又不重送、不進對帳。好在 `hint.turn === cs.turn` 這道閘讓它最多卡到本回合結束，影響有限。

**低-4｜整格 `replaceWith` 可能打斷該格正在播的動畫。** 不過 `patchField` 對同伴那格本來就是同一招（`:1355`），而且 `matePlayShown` 已經處理了淡入重播，風險低、與既有寫法一致。

## 4. 訊息量與免費額度

- 每「換一次選取」1 則、取消 1 則、打出時的 null 1 則。用點選打一張要選目標的攻擊牌 = **最少 2 則**（選 + 打出清掉）。一回合若打 3 張、其中 2 張要瞄準，約 4～6 則；加上猶豫換牌，實測量級大概**每回合 4～10 則（雙方合計）**。同值不重送有擋掉重畫造成的重複，這點有做對。
- **但沒有上限**：`setTargeting` 是同步送，同一張牌連點開/關每次就是 2 則。滑鼠狂點 10 下/秒 ≈ 20 則/秒。
- 中繼是 Durable Object 的 WebSocket，每一則進來的訊息算一次請求，中繼只有 `MAX_MSG` 長度檢查、**沒有任何速率限制**（`worker/src/index.ts:47,107`）。心跳是 25 秒一次（`ws.ts:48`），一間房一小時才 ~288 則，相形之下微不足道。
- 量級估算：一場正常對戰一小時大約多出 ~1000 則，等於把戰鬥中的中繼流量**大致翻倍**（原本每張牌 req+act 2 則、每回合對帳 1～2 則）。十萬/日換算約可支撐 50～100 房小時，正常玩沒問題。**真正的風險是狂點**：20 則/秒持續約 **80 分鐘**就能把全天十萬用完，之後所有人都連不上。加一個 100～150 毫秒的合併／防抖（只送最後一個值）幾乎不影響手感，就能把最壞情況砍掉一到兩個數量級。（→ 中-3）

## 5. `LoopbackPair` 語意 vs 真中繼

**一致，可以放心。** `LoopbackPair` 的 `a.send` 只呼叫 `onB`、`b.send` 只呼叫 `onA`（`transport.ts:118,124`），自己送的不會回到自己；真中繼是 `webSocketMessage` → `this.other(ws)?.send(msg)`，`other()` 明確依角色抓**另一邊**那條連線（`worker/src/index.ts:100-108`），同樣不回聲。第二個測試「自己送的不會回到自己」對應到真實行為。

兩點差異不影響這次測的東西，但講清楚：①Loopback 是同步、保序、不掉包，真中繼是非同步且會在對方關閉時靜默丟棄（見低-3）；②`session.handle` 那道 `m.seat !== this.seat` 讓兩種語意下結果都一樣，所以就算哪天換成廣播式中繼也不會壞。
