## 中

### 中-1　同伴的「你也抽一張／飯糰分你」那類牌，我這台的手牌與飯糰不會重畫

- **玩家看到**：引擎說我多一張牌，畫面上那張牌根本不存在、點不到；飯糰數還是舊的，原本標「餓扁了」變灰的牌仍然是灰的，而灰牌的 onClick 被 `cardview.ts:77` 的 `disabled` 擋死。要等我自己做別的動作或換回合整頁重畫才補上——這一回合等於白給。

### 中-2　同伴動作之後，`patchField` 會把「等對方…／倒下了…看同伴打」那顆按鈕解灰
- **檔案**：`combat.ts:1362`（`if (!canAct() || dealDelay > 0) ... else removeAttribute('disabled')`）；`canAct()` 在 `combat.ts:604`，**不看 `my().ready` 也不看 `my().down`**，只有整頁重畫那條才看（`combat.ts:1421-1426` 的 `iReady`／`iDown`）。
- **時序**：我按完結束回合（或已倒下）→ 同伴出一張牌 → 我這台 light settle → `patchField` → 按鈕被解灰，字還是「等對方…」。
- **玩家看到**：一顆亮著的「等對方…」／「倒下了…看同伴打」。倒下那條按下去會被 `net/action.ts:73` 的 `canApply` 靜靜擋掉、`sendOrDo` 回 false 沒人理（`combat.ts:1732` 沒接回傳值），畫面只是重畫一次——完全就是「按了沒反應」的假象。已舉手那條則會多送一則沒意義的 `ready:true` 出去。
- **修**：`combat.ts:1362` 的條件補上 `|| my().ready || my().down`，跟 `render()` 用同一組判準。

### 中-3　斷線之後戰鬥畫面照樣全部可以點，畫面內的紅字還會被自己按掉
- **檔案**：`session.ts:119`（`onClose` 同時打 `hooks.onClose` 與 `trouble`）、`lobby.ts:91`＋`lobby.ts:65 troubleBanner`、`combat.ts:2508-2512`。
- **先講查過沒問題的一半**：`clearScreenHooks`（`session.ts:168-188`）只清畫面級的 `trouble`，全域橫幅走的是建構式帶進去的 `onClose`／`onDesync`，**不會被清掉**；`.net-trouble` 掛 `document.body`、`position: fixed`、`z-index: 9999`（`ui/styles/screens.css:1490`），換畫面不會被掃掉，只有 `leaveCoop()` 會撕（`app.ts:262`）。所以「斷線看不到紅色橫幅」這件事不成立。
- **問題**：`canAct()`（`combat.ts:604`）不看 `session.stopped`。斷線後手牌、忍具、結束回合全都還是活的。點一張牌 → `act()` 第一行就把 `hint` 清掉（`combat.ts:1846`）→ 牌飛出去 → `sendOrDo` 回 false（只在主控台留一行）→ `settle` 重畫 → 牌彈回手上，**戰鬥畫面裡那行紅字消失**（只剩最上面那條全域橫幅）。而且戰鬥畫面沒有任何「回標題」的出口。
- **修**：`canAct()` 加 `&& !session?.stopped`，並在 `onTrouble` 裡把畫面鎖住、補一顆「回標題」。

### 中-4　`drop` 不看 `n`，任何一則「沒算數」都會解鎖並清掉 `chooseSent`
- **檔案**：`session.ts:477`（`if (m.m === 'drop') { this.dropped?.(); return; }`——訊息帶了 `n`（`transport.ts:58`）卻完全沒用）、`combat.ts:2451`。
- **時序 A（連續兩次 drop）**：客戶端送出牌 A 被主機丟掉；3 秒保險絲（`combat.ts:597`）跳掉後玩家又送出牌 B；此時 A 的 drop 才到 → `unlockSend()` → 玩家可以再送 C，而 B 還在路上。「一次只讓一個動作在路上」這條規則就破了。
- **時序 B（更明顯）**：我按下選牌「確定」（`chooseSent = pd`，`combat.ts:2380`）；一則**屬於前一張牌**的 drop 到達 → `chooseSent = null` ＋ `syncPicker()` → `cs.pending` 還在 → **選牌視窗當場又彈回來**。玩家以為沒選到、再按一次確定，第二則 `choose` 送出去後會被主機 `canApply`（`chooserOf` 已變 -1）再丟一次。
- **玩家看到**：已經關掉的挑牌視窗自己跳回來。
- **修**：`onDropped` 只在 `m.n === this.sentReq`（最新那一則）時才觸發。

### 中-5　主機自己的動作走 `render()` 不走 `settle()`，所以不會叫 `syncPicker()`
- **檔案**：`combat.ts:2481-2483`（`alreadyShown = mine && isHost` → `render()`）；`syncPicker()` 只掛在 `settle()` 尾巴（`combat.ts:2256`）、`onDropped`（`:2451`）與開場（`:2516`）。
- **時序**：出牌與喝忍具包在 `act()` 裡（`combat.ts:1846`），`sendOrDo` 回來之後那支還會補一次 `settle` → 有 `syncPicker`，所以**今天剛好沒事**。但「結束回合」「再想想」「替他收回合」三條是直接呼叫 `sendOrDo`、沒有 `act()` 包（`combat.ts:1732`、`1754`、`1765`）。
- **玩家看到**：目前看不到。這是一顆等著被踩的地雷——哪天有動作會開／關 `pending`（例如收回合時觸發的挑牌），主機那台的視窗就不會跟著開，而 `canAct()` 因為 `cs.pending` 會把兩台一起鎖住、沒有橫幅。
- **修**：把 `syncPicker()` 搬到 `onApplied` 的尾巴，不要只掛在 `settle` 上。

## 查過、確認沒問題的（含模擬過的時序）

1. **舉手＋選牌同時發生**：`combat.ts:2491` 的 `allReady(cs) && !cs.pending` 擋著；`engine/combat.ts:630-631` 的 `beginEnemyTurn` 在有 `pending` 時回 false、**也不清舉手旗標**，所以「舉手齊了但還有人在挑牌」不會把回合收掉；`choose` 套進來時 `onApplied` 會再進來一次，那時 `pending` 已清、`allReady` 仍為 true，兩台各自收回合。模擬過：客戶端挑牌＋主機先舉手、主機挑牌＋客戶端先舉手、`resolveChoice` 的 `remaining` 連開第二個 `pending`（`pd` 是物件比對，`chooseSent` 認不到新的那個、視窗照開）。另外 `onUnready`（`:1752`）雖然沒判 `cs.pending`，但收回舉手兩台會套同一個動作，一致、不分岔。

2. **一方倒下**：`allReady`（`engine/combat.ts:574-577`）只算站著的人；`canApply('ready')`（`net/action.ts:73`）擋倒下的人；`render()` 把按鈕換成「倒下了…看同伴打」並反灰。倒下那台手上沒牌 → `collectHand()` 回 0（`combat.ts:1671`）→ 當場同步跑 `runEnemyTurn()`，另一台要等收牌動畫，兩台開演差好幾百毫秒——但 `endOfTurn` 是**各自記下自己那一份再配對**（`session.ts:299-319`），不會誤判分岔。模擬過：座位 0 倒、座位 1 倒、倒的那位是主機／是客戶端。

3. **誰先舉手**：主機的 `submit` 是同步套用的，`onApplied` 在 `sendOrDo` 那一行之前就跑完，所以鎖只給客戶端（`combat.ts:391-393`）；`onEndTurn` 的 `if (!collecting && !enemyTurnRunning) render()`（`:1734`）擋掉「主機是最後一個舉手」時把飛到一半的手牌打回原位。四種先後組合都走過。

4. **`beginEnemyTurn` 回 false**：兩種來源——有 `pending`（被 `:2491` 擋掉）、`phase !== 'player'`。後者要同時 `allReady` 成立，而出牌／喝忍具的人一定不是 `ready`（`canPlay`、`canUsePotion` 都擋 `p.ready`），全倒時 `allReady` 直接回 false，所以走不到；就算走到也只是 `settle(deal)` ＋ `release()`（`combat.ts:1795`），不會卡住。

5. **舉手旗標什麼時候清**：`engine/combat.ts:632` 第一行 `for (const p of cs.players) p.ready = false`，兩台各自跑、不傳結果；那段期間 `session.hold()`（`session.ts:151`）把同伴動作全排隊、`canAct()` 擋掉本機操作，所以清旗標這一步不可能被插隊。

6. **進場時間差**：主機還在點關主開場對白（`app.ts:379`）或推關主門（`bossdoor.ts:62-65` 的 900 毫秒），加上 `warmEncounter` 最多 1.5 秒（`app.ts:368`），客戶端可能早就出牌。那些訊息帶 `f`，`drain()`（`session.ts:518-534`）看到 `f > this.fight` 整批留著；`session.attach(cs)` 刻意排在戰鬥畫面**最後一行**（`combat.ts:2582`）才一口氣套下去，回呼與第一次畫面都已就緒。模擬過：客戶端先進場連出兩張牌、主機先進場先舉手、客戶端在 3 秒保險絲之後連點同一張牌兩次（第二次被 `canApply` 擋掉回 drop）。

7. **戰鬥結束兩台判定時機不同**：最後一刀不論誰補，`checkOver()`（`combat.ts:2272-2283`）都掛在 `onApplied` 尾巴（`:2485`），客戶端自己的最後一刀也演得到；`attach(null)` 之後同一場晚到的 `req` 走 `stale()` 回 drop（`session.ts:575-582`），不會留到下一場。`fight` 只在 `attach(cs)` 且 `cs !== lastCs` 時加一（`session.ts:132`），兩台進出場次一樣所以數字一樣。另外我特別確認過：`stale()` 對 `act` 會 `stop()`（報分岔），但主機在 `attach(null)` 之後不可能再發這一場的號碼（`submit` 有 `!this.cs`、`take` 走 `over` 分支），所以那條走不到。

8. **獎勵畫面接手**：先進戰利品畫面那台投的票，在對方還在戰鬥時 `picked` 是 null（`clearScreenHooks` 清掉的），票只被記下來不通知；對方進到戰利品畫面 `onPick` 時由 `replay()`（`session.ts:437-447`）補跑一次，而 `clearScreenHooks` 換畫面會清 `replayed`（`:174`），所以補得到，不會兩個人各等各的。順帶查了 `resolvePendingAfterFight`（`engine/run.ts`）：`forSeat` 只影響提示文字，狀態是照 `standing(run)` 順序兩位都跑，兩台一致。

9. **主機「來不及」那一則 drop**：`take()`（`session.ts:536-566`）兩種丟法（回合對不上、`canApply` 回 false）都會回 `drop`，不會靜靜吞掉；客戶端 `onDropped` 會 `unlockSend()` ＋ `render()` ＋ `syncPicker()`，手牌畫回真實狀態。就算 drop 整包掉了，還有 3 秒保險絲（`combat.ts:597`）兜底，不會永遠按不動。唯一缺口是不比對 `n`（中-4）。

10. **`beforeApply` 快照與 `settle(light)`**：`beforeApply` 在 `queue.receive` 之前被叫（`session.ts` 的 `ingest`），快照一定落在「套用前」；號碼還缺的那幾則只會覆寫快照、不會提早消耗，接得上時一口氣比對，演出不會錯位。`handsBefore` 只是 `p.hand.slice()` 的唯讀複本，`matePlays`（`src/ui/mateplay.ts`）是純函式、不碰引擎——**同伴出牌顯示確定不影響鎖步**。

11. **`hold`／`release` 會不會永遠停在 held**：`release()` 在 `runEnemyTurn` 兩個出口都有（`combat.ts:1795`、`:1809`）；`step()` 在 `app.cs !== cs` 時提早收手不 release，但那一刻必定是 `checkOver()` 先 `attach(null)`（`session.ts:136` 把 held 放掉）之後才發生；真的漏了，下一場 `attach(cs)` 也會歸位（`session.ts:132`）。`drain()` 的 `draining` 旗標讓迴圈裡被叫到的 `release()` 不會重入，外圈會接著跑完。

12. **新加的 `hint` 通道**：`session.ts:245-248` 送、`:477` 收（擺在 `dead` 檢查之後、`cs` 檢查之前，收得到），`clearScreenHooks` 有清 `hinted`（`:180`），不進 `submit`、不進 `syncCheck`、不碰引擎——**不會造成分岔**。`setTargeting`（`combat.ts:447-451`）用 `hintSent` 去重、`onEndTurn` 與 `pickTarget` 都會送 `null`，不會洗版。

**不確定的部分（誠實標註）**：以上全是靜態讀＋時序推演，沒有實機兩台對打驗證；中-1／中-2 我沒有寫測試去跑實際 DOM，是從 `patchField` 沒有碰到 `.hand`／`.energy`／沒有判 `ready`／`down` 這兩件事直接推出來的。另外 `overlayRoot()` 回 null 會讓挑牌視窗靜靜不開、而 `cs.pending` 又會把兩台一起鎖死且沒有橫幅——但 `setOverlayRoot` 在 App 建構式就呼叫（`app.ts:71`），實務上碰不到，所以沒列進去。
