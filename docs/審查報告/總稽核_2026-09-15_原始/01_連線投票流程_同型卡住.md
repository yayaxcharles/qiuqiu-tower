## 高-2　`reward.ts:93-96`：「秘寶進背包」這件事綁在**動作套用成功**上，動作被拒絕就永遠湊不齊 → 兩台一起停在戰利品畫面

**位置**：`reward.ts:95`（`coop.submitRun` 回傳值沒人看）＋ `reward.ts:71-74` `markRelicSeat` ＋ `runaction.ts:54`

`canApplyRun` 對 `relic` 的規則是 `return !p.down && !p.relics.includes(a.id);`。被判 false 時，主機走的是**搶標規則**（`session.ts:598`）——靜靜不發號碼、什麼都不回。於是 `onRunApplied` 永遠收不到那一則 → `markRelicSeat` 不會被叫 → `r.relicTaken` 永遠 false → `maybeGo()` 每次都在 `if (offers.length && !r.relicTaken) return`（112 行）提前收工。

**玩家會看到**：牌挑完了、秘寶也點了、兩邊底下都寫著「等對方…」而且是灰的，永遠走不了，只能兩邊重開。

**可觸發性（誠實標註）**：`rollRelicChoices`（`rewards.ts:118-130`）開牌時會把**兩個人身上已有的**都濾掉，所以開牌當下踩不到。踩得到的是「開完牌、還沒挑完之前又拿到同一件」——例如事件 `afterWin` 的秘寶由 `resolvePendingAfterFight` 在 `afterCombat` 裡發，而它走的 `rollRelic` 只避開那一位自己身上的，不知道戰利品已經開了哪兩件。**我沒有實際跑出一組資料證明它會撞，所以這條的「今天會不會發生」我標不確定**；但「動作被拒絕→旗標永遠湊不齊」這個結構本身是實在的，而且同一件事在 `chest.ts` 不會卡死（那邊的放行看的是 `done` 動作，不是 `relic` 動作）。

**修法**：93 行的條件改成「`got[i]` 是 null **或那一位本來就有那件／已倒下**就直接 `markRelicSeat(i)`」，並且 95 行的 `submitRun` 回 false 時也補記一次（`got` 兩台算出來一樣，各自在本機記不會分岔）。

## 中-1　`actclear.ts:172`：補跑的票會把「關主信物先亮一次」那一頁洗掉；而且結算之後 `onPick` 沒拆，任何遲到的同類票會把結果頁蓋回三選一

**位置**：`actclear.ts:166-180`（`onPick`）、`172`（`render()`）、`186-203`（`bossRelic` 早退）

**觸發時序（票先到／畫面後到）**
打完關主之後，兩個人各自**手動點完過關幻燈片**才進 `actclear`——這是整局裡兩台落差最大的一段（可以差好幾秒）。A 點得快，收下信物、挑好、按「出發」，送出 `actrelic`＋`actcard`。B 還在看幻燈片（畫面名還是 `combat`，`picked` 是 null），兩票被靜靜記進票箱。

B 進 `actclear` → `clearScreenHooks('actclear')` 清掉 `replayed` → 166 行 `coop.onPick(...)` 註冊 → `session.ts:432` 排一次 `replay()` → 但 B 的畫面此刻是 186 行的「關主的信物／收下」那一頁。下一拍 `replay()` 把 A 的票補給處理函式 → 172 行 `render()` → `clearKeepBg(root)` 把信物頁整個換成三選一。

**玩家會看到**：打倒關主後，那顆「收下」還沒按到就消失了，信物的亮相整段沒出現，畫面直接跳成秘寶／牌三選一。（流程本身會走完，不會卡死。）

**同型的第二個風險**：結算之後 `done(mine)` 只是 `clearKeepBg` + 重畫，**沒有換畫面、也沒有重新註冊**，所以那支 `onPick` 還掛著；`advanced` 要等玩家按「帶著它上塔頂」才變 true。這段期間只要再有一張 `actrelic`／`actcard` 票進來（票箱已被 `clearPicks` 清空 → `allVoted` false），就會 `render()` 把結果頁蓋回三選一，而且 `sent` 變回 false、`pickedRelic` 還留著——再按一次「出發」就是**第二輪投票**，對面若已 `advanced` 就永遠收不到，我這台停在「等對方挑完…」。目前找不到會送出第二張票的來源，所以我只把它當作**沒有護欄**，不當作今天會發生。

**修法**：`onPick` 裡在還沒結算完成前，先判斷「現在畫面是不是還停在信物頁／結果頁」，是的話不要 `render()`（`chest.ts:89` 的 `if (openedCoop) revealCoop();` 就是正確示範）；並在 `done()`／`go()` 裡把 `advanced` 之外再加一個「已結算」旗標擋住 172 行。

> 附帶：`reward.ts:161-178` 有一模一樣的「信物先亮一次」早退，但 `afterCombat` 對 `rewards.kind === '塔主'` 一律轉去 `actclear`／`result`，戰利品畫面收不到那個 kind，所以那段是死碼、沒有這個問題。只有 `actclear` 中。

## 中-2　`shop.ts:58` / `rest.ts:45`：「我這格弄完了」的記錄住在畫面的區域 `Set` 裡，比畫面早到的那一則永遠遺失 → 一台卡在店裡／貓窩

**位置**：`shop.ts:58`（`const done = new Set<number>()`）、`shop.ts:268-276`；`rest.ts:45`、`rest.ts:216-250`（`allDone()` 在 243 行）

**觸發時序（對方比我快一個畫面）**
走格子投票時，**後投的那一位是同步結算**、當場 `enterNode`；先投的那一位要等票的訊息繞回來（一個來回）才結算。所以兩台進罐頭鋪／貓窩的時間本來就差一個 RTT。

在這個空檔裡，`app.coop.clearScreenHooks('map')` 已經把 `runApplied` 設成 null，而地圖畫面**從來不註冊** `onRunApplied`。同伴若在這段期間送出 `{t:'done'}`（罐頭鋪的「逛好了」）或 `{t:'rest'}`（貓窩的「打盹」），`session.ts:613` 的 `this.runApplied?.(r.applied)` 是個 no-op——**動作照樣套進引擎（不會分岔），但畫面層的那筆記錄永遠補不回來**（`done` 是區域變數，`replay()` 只補票箱、不補動作）。

**玩家會看到**：我按「逛好了」，鈕變成「等對方逛完…」而且是灰的，永遠不會走；同伴那台早就上樓了，在地圖上點格子等我投票，我這邊根本不在地圖上。兩個人互相等到天亮。

**時序窗有多寬（誠實標註）**：就是一個 RTT（約 50–300 毫秒），要同伴一進店／進窩就立刻按到那顆鈕。不是天天發生，但**一旦發生就是永遠停住**，而且沒有任何提示。

**修法**：把「誰弄完了」從畫面的區域 `Set` 搬到會話上（跟票箱同一個位置，換畫面不清），或在 `session` 補一份「還沒交給畫面的整局動作」清單，讓畫面註冊 `onRunApplied` 時像 `replay()` 一樣補跑一次。

## 低-1　`actclear.ts:152`：一次按鈕送**兩張票**，中間不是原子的
```ts
if (coop) { coop.pick('actrelic', pickedRelic ?? ''); coop.pick('actcard', pickedCard ?? ''); return; }
```
第一張 `pick` 會同步觸發處理函式（`actcard` 還沒齊 → `render()` 整頁重畫），第二張才送出去。正常情況沒事（我實際跑過先投／後投兩種順序，結算都對稱）。但若連線剛好在這兩行之間斷掉／`pick` 回 false，`actrelic` 就成了一張孤票，對面永遠等不到 `actcard`。**修法**：合成一張票（`pick('actpick', `${relic}|${card}`)`），或第二張送失敗時把第一張的狀態畫回可重按。

## 低-2　`event.ts`：`gamble` 的輸贏兩邊若哪天放進互動效果，兩個座位的 outcome 種類就會不同 → `evlearn`／`evcard` 永遠湊不齊

**今天走不到**：我把 `content/events.ts` 裡的 `gamble` 全掃過，win/lose 只有 `maxHp`／`addCard`／`relic`／`fish`／空陣列，沒有互動效果。**修法**：在 `take()` 裡加一道「我的 outcome 不需要挑牌就補一張空票」的保險，別依賴資料一直維持現狀。

## 低-3　`shop.ts:53`：我還沒進店，同伴的買賣會被主機靜靜丟掉
`coop.attachShop(shop)` 要等我進入罐頭鋪才掛上。在那之前我若是主機，`canApplyRun` 的 `case 'buy': if (!shop) return false` 會讓那則請求走「搶標」路徑——**不發號碼、不回 `drop`、什麼都不說**。同伴按了買東西完全沒反應、沒音效、貨架也不變。窗口同樣是一個 RTT。**修法**：`attachShop` 提前到 `enterNode` 決定走進罐頭鋪的那一刻，或對 `rreq` 被拒也回一則 `drop`。

## 低-4　`combat.ts:604` + `2331`：`cs.pending` 解不掉的話兩台一起凍住（不確定引擎有沒有防線）
`canAct()` 只要 `cs.pending` 在就全程回 false，而 `onApplied`（2491 行）收回合的條件是 `allReady(cs) && !cs.pending`。所以只要 `pending` 解不掉——例如挑牌那位的視窗因為 `pd.min` 大於能挑的張數而「確定」永遠按不下去（2355 行 `bad = chosen.length < pd.min`）、或挑牌的那位中途倒下——**兩台都不能出牌、也收不了回合，連「強制收回合」都沒用**（`force` 只設 ready，過不了 `!cs.pending` 那一關）。
**我沒有驗證引擎有沒有把 `pd.min` 夾到可選張數，也沒有驗證倒下時會不會清 `pending`**，所以只列為需要確認的點。

# 查過、沒問題的流程（附我模擬了哪幾種時序）

下列每一條我都跑過四種時序：**① 我先投／② 我後投（`pick` 會同步結算並清票箱）／③ 票先到、畫面後到（我還在上一個畫面，票被記進票箱、之後靠 `replay()` 補）／④ 同一畫面重畫（`app.show` 自己叫自己）**，另外加測「一方倒下」。

1. **`map.ts:129-140` 走格子投票** — 四種＋倒下全過。後投那一位的 `coop.pick('map', n.id)`（257 行）是點擊處理函式的**最後一行**，投完不再讀票箱，沒有 `event.ts` 那個坑。`app.show('map')` 自呼叫時 `clearScreenHooks` 因為畫面同名不清 `replayed`，補跑最多多叫一次處理函式就收斂（第二次 `replayed.get('map') >= box.size` 擋掉），不會無限迴圈。倒下的人 250 行直接 `return`，票也被 `onlyStanding` 洗掉。

12. **`bossdoor.ts`** — 沒有任何連線協調，兩個人各自推門、各自 `startFight`。這樣是安全的：晚進場那台收到的戰鬥動作會因為 `f > this.fight` 留在 `backlog`（`session.ts:526`），`attach` 之後照號碼補套，不會掉動作也不會判分岔。

## 關於 `replay()` / `replayed` / `lastScreen`（題目點名的那一項）

- **重複補是常態、不是例外**：同一張票會通知處理函式兩次——`record()` 直接叫一次（`session.ts:454`），換畫面後 `replayed` 被清空、`replay()` 再叫一次。所以**每個處理函式都必須對「同一票被叫兩次」免疫**。map／event／chest／reward 都有旗標擋著；`actclear.ts:172` 沒有（中-1 的第二段）。
- **目前沒有漏補**：`replayed` 用「票數」當鍵、同畫面名重畫時不清，所以只有「票數沒變但需要重新結算」才會漏——而每一票都會讓 `box.size` 變大、結算完又馬上 `clearPicks`（同時 `replayed.delete`），湊不出這種情形。但這是**靠「票不能改」撐住的**：哪天加上改票，`replay()` 立刻開始漏。
- **真正會出事的是 `lastScreen` 只比對畫面名字**：`actclear` 的「信物先亮一次」、`event` 的 `panel()`／`chooseCard()`、`chest` 的 `revealCoop()`、`shop`／`rest` 的 `render()` 都不走 `app.show`，`lastScreen` 看不見它們。`replay()` 於是會在玩家正站在那些子畫面上的時候把票補下去，處理函式一 `render()` 就把子畫面洗掉——中-1 就是這麼發生的。
