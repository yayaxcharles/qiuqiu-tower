# 逐條清單

## 高（3 條）

### 高-1　開房的人等不到 2.5 分鐘就被中繼自己踢掉
- **檔案**：`F:\ClaudeWork\qiuqiu-coop\src\net\ws.ts:85`（`ping` 的 `setInterval` 在 `wrap()` 裡）與 `:125`（`ready: opened.then(() => wrap(ws))`）；`F:\ClaudeWork\qiuqiu-coop\worker\src\index.ts:44`、`:115-121`
- **會發生什麼**：心跳只有在中繼回 `open`（對方加入）之後才開始送。開房的人在等朋友輸入房號的那段時間**一則 ping 都沒送**，而中繼的鬧鐘在第三次掃描（約開房後 180 秒）就會判定他是殭屍、`bye()` 掉他。`bye()` 這時 `other` 是 undefined，走到 `index.ts:131` 的 `ws.close()`——**沒帶代碼也沒帶原因**，所以 `ws.ts:73` 的 `ev.reason` 是空字串，玩家看到的是「連不上中繼伺服器（網路不通，或伺服器沒開）。檢查網路之後再試一次」。他明明連著、網路也好好的。用 LINE 把房號講給朋友、朋友再開遊戲、再打六位數——超過三分鐘完全正常。`tests/net/ws.test.ts:95` 那條測試正好把這件事釘死了（「**連上之後**每 25 秒送一次 ping」），設計稿 `docs/連線版_房號中繼_設計稿.md:26` 寫的卻是「瀏覽器每 25 秒送 ping」。實作與設計對不上。
- **怎麼修**：`hostRoom()` 拿到 `hosting` 之後就開始送 ping（把心跳從 `wrap()` 抽出來、連上時啟動、`wrap`／`cancel` 接手清掉），或中繼對「還沒配對的 host」放寬殭屍判定。

### 高-2　中繼沒有任何防護，一兩分鐘就能把整天的免費額度打爆
- **檔案**：`worker\src\index.ts:28-35`（Worker 入口）、`:60-64`（Room.fetch）、`:106-109`（`webSocketMessage`）
- **會發生什麼**：沒有 Origin 檢查、沒有任何認證、連線與訊息都沒有速率限制。`MAX_MSG` 只擋單則大小（16 KB），不擋頻率。中繼網址 `qiuqiu-relay.qiuqiu-tower.workers.dev` 硬寫在 `ws.ts:21`，會被打包進公開的 GitHub Pages 檔案裡，任何人抓得到。一條 socket 每秒送上千則、每則就是一次 Durable Object 請求，**免費方案的每日額度大約兩分鐘內見底**；額度用完之後當天（UTC）剩下的時間整個中繼不可用，只能叫使用者切「貼碼直連」。
- **怎麼修**：加三道——`fetch` 檢查 `Origin` 只放行自己那兩個 GitHub Pages 網域；每條 socket 記一個每秒訊息上限（例如 30 則／秒，超過就帶原因關掉）；`env.ROOM` 之前套 Cloudflare 的 Rate Limiting binding 擋掃房號。

### 高-3　`fetch` 沒有 try/catch，`hosts[0]!.send()` 會把加入者變成 1006
- **檔案**：`worker\src\index.ts:28-35`（Worker 的 `fetch`）、`:86-92`（`server.send` / `hosts[0]!.send` / `setAlarm` 都沒包）
- **會發生什麼**：`index.ts:89` 在把加入者接進來之後、對已經存在的 host socket 呼叫 `send`。如果那條 host 剛好正在關（背景分頁、網路切換），`send` 會丟例外，整個 `Room.fetch` 就拋出去→ Worker 回 500 → 瀏覽器只看到 close code 1006、`reason` 是空的 → 玩家看到「連不上中繼伺服器（網路不通，或伺服器沒開）」，訊息完全指錯方向。同一支檔案裡 `bye()`（`:128-131`）就有好好包 try/catch，這裡漏了。另外 `:92` 的 `storage.setAlarm()` 若拋出，socket 已經 `acceptWebSocket` 了卻還是回 500，而且那間房從此沒有殭屍清掃。
- **怎麼修**：`index.ts:89` 與 `:87` 的 `send` 各包一層 try/catch（送不到就當 host 已走、退回 4404），`getAlarm/setAlarm` 那行也包起來，外層 `export default fetch` 再加一個 catch-all 回 503。

### 中-3　「考慮中」提示只有客戶端節流，狂點兩張牌約 1.7 小時就能燒光當日額度
- **檔案**：`src\ui\screens\combat.ts:448-461`（120 毫秒合併）、`worker\src\index.ts:106-109`（中繼端零限制）
- **會發生什麼**：120 毫秒的合併把每人上限壓到約 8 則／秒，兩個人就是約 16 則／秒；每則都是一次 Durable Object 請求。10 萬 ÷ 16 ≈ 6250 秒 ≈ **1.7 小時**。這不需要惡意，一個小孩在兩張牌之間亂點就做得到，而且客戶端的節流是可以被繞過的（限制只在自己這台）。
- **怎麼修**：中繼端加每秒訊息上限（跟高-2 同一個修法），或把 `hint` 的合併時間拉到 300-500 毫秒。

### 中-4　房號可以被掃描佔用，朋友加入時會被卡成「房間已經有人加入了」
- **檔案**：`worker\src\index.ts:26`（`/^\/room\/([0-9]{6})$/`）、`:69-71`（先搶先贏）；`src\net\ws.ts:35-37`（`makeCode`）
- **會發生什麼**：100 萬組房號、沒有速率限制、沒有認證。攻擊者持續掃描就能把 join 的位子搶走，真正的朋友輸入房號時被 4403 擋掉（「這個房間已經有人加入了」），而開房的人完全不知道發生什麼事。搶到位子的人也能對著鎖步協定亂送訊息——好在 `session.ts` 的對帳會抓到分岔並停下來（不會被改壞存檔，連線局本來就不寫存檔），所以是「玩不成」而不是「被玩壞」。
- **怎麼修**：房號改成「六位數字＋一段只有開房的人知道的短密鑰」放在查詢字串裡驗，或直接把房號位元數加大（例如 8 碼英數）。

### 中-5　雲端的 `npm ci` 為了一個型別檢查多拉約 140 MB
- **檔案**：`package.json:16`（`"wrangler": "^4.131.2"`）、`.github\workflows\deploy.yml:32`、`:42`
- **會發生什麼**：實測 `node_modules` 裡 `@cloudflare/workerd-<平台>` 一包就 95 MB，加上 `miniflare` 27 MB、`wrangler` 15 MB，總共約 140 MB；鎖檔多了 13 個相依。`actions/setup-node` 的 `cache: npm` 快取的是 `~/.npm` 的壓縮包，不是 `node_modules`，所以每次 CI 還是要解壓那 140 MB。而中繼根本不是由 CI 部署的，等於每次改網頁都在為一個型別檢查付這個成本。粗估多 20-40 秒（首次更久），不確定精確數字。
- **怎麼修**：把 `wrangler` 從根 `package.json` 搬到 `worker/package.json`，或把那個型別檢查拆成獨立的 job（跟網頁的 build 平行跑，不擋部署）。

# 「最壞情況一天會用掉多少請求」（Cloudflare 免費方案）

**先講不確定的地方**（請以 Cloudflare 當前文件為準，我沒有實測帳單）：
- Workers 免費方案每天 10 萬次請求，這條我有把握（設計稿 `docs/連線版_房號中繼_設計稿.md:44` 也是這樣寫的）。
- Durable Object 的請求額度**是否跟 Workers 那 10 萬共用、還是另外一條線**，我不確定；我的理解是分開計、DO 免費方案另有自己的每日請求與 GB-s 上限。
- 「每一則進來的 WebSocket 訊息＝一次 DO 請求」「鬧鐘每次觸發＝一次 DO 請求」「`setWebSocketAutoResponse` 回的 pong **不計**請求」——這三條是我對計費文件的理解，方向我有信心，數字請自己再對一次。
- 鬧鐘每分鐘喚醒一次對 GB-s（時長費）的影響，我不確定每次喚醒的最小計費單位，所以下面只算請求數、不算 GB-s。

**一次連線會產生兩筆**：瀏覽器打進來先過 Worker（1 筆），Worker 再 `env.ROOM.get(...).fetch(req)` 打進 Durable Object（1 筆）。

| 情境 | 一天大概用掉 |
|---|---|
| 兩個朋友玩 8 小時（正常） | 連線重試約 100 筆＋鬧鐘 480 筆＋遊戲訊息 1～3 萬筆 ≈ **1.5 萬～3.5 萬**。在額度內，但設計稿寫的「一局幾百則、遠遠用不完」偏樂觀——`hint` 那條就把訊息量放大了一個量級。 |
| 兩個人狂點兩張牌互相切換（不需惡意） | 約 16 則／秒 → 10 萬 ÷ 16 ≈ **6250 秒（約 1.7 小時）就見底**。 |
| 一條 socket 全速灌訊息（惡意，中-3／高-2） | 每秒上千筆 → **約兩分鐘燒光當日 10 萬**，之後整天中繼不可用。 |
| 掃房號（高-2／中-4） | 每次連線 2 筆（Worker＋DO）。掃 5 萬個房號就是 10 萬筆 → **Worker 額度在掃完 1/20 的房號時就沒了**。 |
| 100 萬間房全被佔住且都連著（純理論上限） | 光鬧鐘就是 100 萬 × 1440 = **14.4 億筆／天**。實務上額度會先爆，永遠到不了這個數字。 |

**一句話**：目前的設計在「兩個朋友正常玩」是完全夠的，但**沒有任何一道防線擋住「一個人用 curl 迴圈就能讓當天所有人都玩不了」**。額度爆掉的救命索是大廳那顆「改用貼碼直連（備用）」（`lobby.ts:244`），這點設計得不錯。

# 查過、沒有問題的（不湊數，這些是真的看過）

**存檔隔離（第 3 項，全部乾淨）**
- `src\engine\save.ts:29-36`：`PREFIX` 照 `import.meta.env.BASE_URL` 走，`vite.config.ts:14-16` 的 `SITE_NAME` 由 `GITHUB_REPOSITORY`（雲端）或 `SITE_NAME`（推送閘門 `prepush_gate.sh:80-84`）決定，兩個倉庫確實會拿到 `qiuqiu-tower/*` 與 `qiuqiu-tower-coop/*` 兩套鍵。本機與測試退回單機版前綴，符合註解寫的。
- 連線局不會被存成單機檔：`app.ts:244-247` 的 `save()` 擋 `coop`、`result.ts:35-38` 也擋了一次（兩個呼叫點都補上了）。反過來也不會：`app.ts:200` 與 `:162` 的 `continueRun`／`newRun` 進來第一件事都是 `leaveCoop()`。
