# 動作素材、首載圖片與程式分包稽核

稽核日期：2026-09-20。量測目錄為本工作副本最新建置的 `dist`。本輪沒有調降圖片品質、縮小圖片、提高預算或修改遊戲規則。

## 可核對結論

先前顯示 15.7 MB「圖片首載」的主因，是檢查器把未被素材清單引用的 `public` 工作檔也算進首載；瀏覽器不會取得這些檔案。17 張純測試用封封 RGB 場景備援已移到 `tools/motion-art-source/fengfeng-extra/scene-fallbacks/`，共 1,440,358 位元組，不再進部署包。

分類修正後仍可重現一項真問題：`main.ts` 在標題顯示後依序執行 `preloadArt()` 與 `preloadAct(1)`，而原本的 `preloadAct(1)` 會載入第一關所有關主階段圖。這讓 22 張尚未遭遇的第二、三階段立繪提早下載，共 717,086 位元組。

現在 `preloadAct()` 只暖載該關所有可能敵人的基礎姿勢；確定遭遇後，`warmEncounter()` 會在進入戰鬥前載入該敵人的基礎與全部階段姿勢。全清單共 52 張階段圖、1,593,450 位元組，已獨立列入「遭遇預熱」。遭遇當下仍已備妥所有姿勢，不會延後到第一次出招才下載。

逐格動作圖也不是一般網址首載。最新四位角色與敵人共有 65 張逐格 WebP、56,507,154 位元組，只在動作模式或實際登場角色需要時載入。一般網址的首張標題畫面不會要求任何 `assets/motion/**`。

## 瀏覽器實際載入階段

以假 `Image` 記錄每次 `src` 指派，並回查 `public` 原檔大小，可把標題後的兩次暖載分開核對：

| 時點 | 新增唯一圖片 | 位元組 |
|---|---:|---:|
| 標題顯示後的 `preloadArt()` | 404 | 6,998,402 |
| 接續的 `preloadAct(1)` | 178 | 3,364,704 |
| 合計 | 582 | 10,363,106 |

修正前合計是 604 張、11,080,192 位元組；差額正好是 22 張階段圖、717,086 位元組。`preloadArt()` 完全沒有載入敵人圖，因此不需修改；問題與修正都只在 `preloadAct()` 與 `warmEncounter()` 共用的敵人網址選取邏輯。

選定角色後的角色素材屬於第二階段暖載，不是標題首載。它與逐格動作包也分開計算。

## 遭遇覆蓋範圍

`enemyIdsForAct()` 仍依 `ACT_ENEMIES` 加上各關關主形成候選敵人集合。`preloadAct()` 對這個集合載入五種基礎姿勢：`idle`、`attack`、`hurt`、`block`、`down`。`warmEncounter(enemyId)` 只處理實際抽中的敵人，並追加其素材清單中所有 `_p2`、`_p3` 等階段的相同五種姿勢。

單元測試使用有基礎與第二階段素材的 `nekomata` 驗證兩個邊界：分關暖載不得要求第二階段；遭遇暖載必須補齊該階段全部五種姿勢。這同時避免為了縮減首載而漏掉實戰換階段圖。

## `public`、素材清單與重複打包

目前未引用圖片只有 3 張、379,500 位元組，都是同一封封事件的來源候選，未列入素材清單：

- `assets/bg/event_fengfeng_fallen_rack_source_i2.webp`：58,276 位元組。
- `assets/bg/event_fengfeng_fallen_rack_source_i3.webp`：289,462 位元組。
- `assets/bg/event_fengfeng_fallen_rack_source_r1.webp`：31,762 位元組。

沒有發現逐格 WebP 被同時嵌入 JavaScript。`public` 原檔由 Vite 複製成一份帶內容雜湊的 `dist` 檔；動作 JSON 只保存檔案路徑、裁切框、腳底支點與時間，不包含圖片二進位。同一材質的多個動作也由影像快取依網址去重。
