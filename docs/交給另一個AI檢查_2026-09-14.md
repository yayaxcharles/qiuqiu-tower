## 一、這是什麼、在哪裡

繁體中文的網頁牌組肉鴿（像《殺戮尖塔》），TypeScript + Vite + Vitest，純前端、沒有後端。

| | |
|---|---|
| 倉庫（連線版，功能最全） | `F:\ClaudeWork\qiuqiu-coop`，分支 `coop` |
| 線上 | <https://yayaxcharles.github.io/qiuqiu-tower-coop/> |
| 部署 | `git push coopdeploy coop:main` → GitHub Actions 跑 `npm test` 與 `npm run build` → Pages |
| 單機版（舊、**沒有菲菲**） | 分支 `main`，線上 <https://yayaxcharles.github.io/qiuqiu-tower/> |

**菲菲這個角色只活在 `coop` 分支上，從來沒併回 `main`。** 問「線上是哪一版」要先確認在講哪個網站。

### 兩個角色

- **球球**（`hero: 'ninja'`）：近身、靠**隱身**閃掉最痛的那一下、蜷縮每回合重賺。
- **菲菲**（`hero: 'feifei'`）：**毒**＋攻擊牌自帶**蜷縮**（丟完就退）。她的攻擊點數小、段數多。

這個差別決定了很多平衡結論，**改任何怪之前先想清楚會打到哪一邊**：

- 蜷縮是「一池」，多段小攻擊跟單發大攻擊對它沒差 → 傷害拆不拆段影響不到菲菲
- 隱身是「一層擋一下」 → **多段攻擊專打球球**
- 穿透（`pierce`）蜷縮擋不住、但隱身閃得掉 → 專打菲菲、球球有解
- 鱗甲（`plating`）每被打一下剝一層 → 多段牌剝得快，但小點數攻擊會被吃掉

### 機器人（平衡測試的主力）

`smartRun(seed, difficulty, hero)` 跑完整一局並回傳統計，在 `src/engine/smartbot.ts`。
**它是決定性的**：同一顆種子永遠跑出同一局，所以改動前後可以逐字比對。

```ts
import { smartRun } from '../src/engine/smartbot';
const r = smartRun('seed-1', 3, 'feifei');
// r.won        這局有沒有通關
// r.act, r.floor  死在第幾關第幾層
// r.diedTo     死在哪個遭遇
// r.fights[]   每一場：{ id, floor, won, hpLost, turns }
// r.bosses[]   每個關主：{ id, won, hpIn, maxHp, turns }
```

現成的報告（直接跑，結果印在 console）：

```bash
npx vitest run tests/smart.report.test.ts       # 通關率、各關到達率、陣亡排行、每個關主的勝率
npx vitest run tests/balance.report.test.ts
```

要自己量的話，在 `tools/` 下開一支 `_xxx.test.ts`（`tools/` 也會被 vitest 掃到），
用 `writeFileSync` 把結果寫出來——**`console.log` 在 vitest 裡會被吞掉**。用完記得刪。

難度 3 跑 400～600 局大約 30 秒。少於 300 局的差異多半是雜訊。

## 三、絕對不能破壞的三條

### 1. `src/engine/` 必須完全決定性

連線版是**鎖步**（兩台各自算，只傳「我打了哪張牌」這種動作，不傳狀態）。
所以引擎裡：

- **不准有 `Math.random`**（要亂數一律走 `cs.rng` / `runRng(run)`）
- **不准讀時間**（`Date.now`、`performance.now`）
- **不准有模組層級的可變狀態**
- 兩台消耗的亂數次數必須一模一樣——加一次 `rng.pick` 就會分岔

`tools/engine_pure.test.ts` 在盯這件事。

### 2. 改連線的東西不可以動到單機

判準是**逐字比對**，不是「看起來差不多」：

```ts
// 改動前後各跑一次，輸出必須一字不差
for (const hero of ['ninja','feifei']) for (let i=0;i<30;i++) smartRun(`det-${i}`, 1, hero)
```

### 3. 修好的每個 bug 都要補一條**會反向變紅**的測試

作法：修好之後，把修正改回壞的寫法，確認測試真的紅，再改回來。
沒做這步的話，測試很可能是恆真的——這個專案已經發生過好幾次。

## 六、這個專案最常見的失效模式：**靜音**

以下每一個都真的發生過，共同點是**畫面正常、不報錯、測試全綠**：

| 發生過的事 | 為什麼沒被抓到 |
|---|---|
| 連線牌 27 張永遠抽不到 | 人數參數沒傳下去，`pickable` 吃預設值 1 |
| 加入的那位的秘寶整場不發動 | 只有座位 ≥1 踩得到，單機與開房那位都正常 |
| 同伴的立繪被自己的蓋掉 | `querySelector('.unit.player')` 沒帶座位，拿到第一格 |
| 菲菲講球球的台詞 | 只把句尾的「喵」拿掉，口氣沒換 |
| 菲菲打完師父放球球的結尾影片 | 開場影片有擋角色，結尾那支漏掉 |
| 部署連續失敗一整天 | 只看 `git push` 成功就宣稱上線，沒看 Actions |

**推論**：這個專案不能只靠測試綠就宣稱完成。要嘛開瀏覽器真的玩過，
要嘛把數字量出來。連線功能一定要**開兩個分頁對打**，而且**一邊球球一邊菲菲**——
只有座位 1 以上、兩邊角色不同時才踩得到的坑最多。

部署完一定要等 GitHub Actions 跑到 `success`，再抓線上首頁比對 `assets/main-*.js` 的雜湊。

## 七、檔案地圖

```
src/engine/          引擎（決定性，見第三節）
  combat.ts          一場戰鬥：回合、出牌、魔物行動
  effects.ts         每一種牌的效果實作
  actions.ts         傷害、蜷縮、抽牌、秘寶發動這些基礎動作
  run.ts             一局：地圖、獎勵、商店、事件結算
  rewards.ts         抽牌／抽秘寶
  smartbot.ts        會玩的機器人（平衡測試用）
  hero.ts            角色差異（起手牌、起始秘寶、牌名、代名詞）
src/content/         資料表（怪、牌、秘寶、忍具、事件、台詞）
src/ui/              畫面（每個畫面一支在 screens/）
src/net/             連線（WebRTC、鎖步）
tools/               生圖與匯出工具，`*.test.ts` 會被 vitest 一起跑
docs/                設計稿與各種匯出的對照表
```

改平衡多半只動 `src/content/enemies.ts` 與 `src/content/cards.ts`。
改完**一定要跑機器人對照**，而且要**兩個角色都跑**。
