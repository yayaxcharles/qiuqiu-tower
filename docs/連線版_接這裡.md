## 架構一句話

**鎖步（lockstep）**：兩邊各跑一份一模一樣的引擎，線上只傳「誰做了什麼」，不傳遊戲狀態。

- 動作分兩條通道，各有各的號碼機：
  - 戰鬥：`src/net/action.ts`（`CoopAction`）→ 套進 `CombatState`
  - 戰鬥以外：`src/net/runaction.ts`（`RunAction`）→ 套進 `RunState`
  - 兩條都是**主機發號碼、兩邊照號碼套用**（`src/net/lockstep.ts`）
- 「大家各選一個」（選路線、挑牌、挑秘寶、事件選項）走另一條**不排序**的通道：
  `session.pick(kind, value)` / `picks(kind, seats)`，兩邊都選完才各自結算（`src/engine/vote.ts`）。
  這種選擇跟先後無關，所以不需要號碼。
- 對帳：每回合結束對一次戰鬥指紋，每走一格對一次整局指紋（`src/net/hash.ts`）。
  對不上就當場停，畫面最上方壓一條紅色橫幅。

## 改這裡的人一定要知道的五個坑

全部是這一批實際踩過、查了很久的。

1. **畫面收尾（`app.disposers`）裡不可以 `clearPicks`。**
   「有人投票 → 重畫畫面」，而重畫是 `app.show()`＝**先跑收尾再重建**，
   於是每投一票就被自己清掉一次，兩邊永遠湊不齊，而且完全無聲。
   清的時機只有一個：**票結算完的那一刻**。

2. **連線的回呼要註冊在早退之前。**
   紙箱、過關、戰利品三個畫面都有「先演一段、然後 `return`」的分支，
   把 `onPick`／`onRunApplied` 擺在函式尾巴就永遠跑不到。

3. **`onPick`／`onRunApplied`／`onApplied` 都是單一插槽**，後註冊的蓋掉前一個。
   同一時間只會有一個畫面在用，所以夠用；但別假設自己註冊的還在。

4. **主機的動作是同步套用的。** `submitRun`／`submit` 還沒回來，`onApplied` 就已經被叫到了。
   所以「動作之後才設的旗標」在回呼裡讀到的是舊值（貓窩那邊因此畫出兩份狀態列）。
   要判斷「這一批是不是我做的」，看 `applied` 裡的座位，不要看外面的旗標。

5. **客戶端的畫面慢一個來回。** 它可能在魔物已經倒下之後才送出一張牌——
   那**不是分岔**，是來不及。主機回一則 `drop`、不編號就好；真正的分岔靠指紋抓。
   客戶端這邊也上了鎖：送出到繞回來之間不收新動作（`inflight`）。

## 查問題的工具

- 網址後面加 `?debug` → `window.__app`（`app.coop`、`app.run`、`app.cs` 都摸得到）。
  **打包版才連得起來**（開發伺服器一改檔就重新整理、連線當場斷），所以不能只靠 `import.meta.env.DEV`。
- 連線出問題會在畫面最上方壓一條紅色橫幅，**第一則訊息留著不被後面的覆蓋**
  （分岔的處理順序是「先報原因、再關連線」，覆蓋的話只會看到沒資訊量的「自己關掉了」）。
- `session.pick()` 被擋下來會在主控台出聲。
